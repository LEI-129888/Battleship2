## 1. Especificação dos Code Smells & Configuração

Para a implementação do Quality Gate automatizado, configurou-se a inspeção estática do Qodana em projetos Java (Maven, OpenJDK 21) para detetar dois *code smells* principais:

**A. Long Method**
- **Inspection ID:** `NonCommentSourceStatements`
- **Limiar (Threshold) Configurado:** 16 linhas (valor situado entre o limite "alto" e "muito alto" apresentado na tabela 2.2 do livro *Object-Oriented Metrics in Practice*, no guião da disciplina).

**B. Overly Complex Method**
- **Inspection ID:** `CyclomaticComplexity`
- **Limiar (Threshold) Configurado:** 10 ramificações/caminhos.

**Ficheiros de Configuração Criados:**
- `qodana-129888.yaml` (na raiz do repositório, com a propriedade Maven).
- `.qodana/profiles/profile-129888.yaml` (perfil customizado com os limiares e inspeções ativadas).
- `.github/workflows/qodana-smell-129888.yml` (pipeline do GitHub Actions com suporte a análise diferencial em PRs).

## 2. Evidências do Quality Gate (GitHub Actions)

O ciclo de testes do Quality Gate exigiu a validação de que o pipeline bloqueia falhas de métrica e passa com sucesso após a respetiva refatoração/correção:

## 3. Conclusão

A integração do Qodana em modo de *Pull Request* permitiu monitorizar de forma incremental a qualidade do código, avaliando apenas as alterações submetidas sem penalizar o PR pelas métricas (dívida técnica) já existentes na *branch* `main`.
O Quality Gate provou ser uma ferramenta eficaz para automatizar a verificação rigorosa dos limiares para os *smells* "Long Method" e "Overly Complex Method", bloqueando a integração de código fora dos padrões e garantindo a manutenibilidade do projeto.
